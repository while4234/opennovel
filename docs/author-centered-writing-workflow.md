# 以真实作家工作方式为中心的 AI 小说创作流程

## 目标与原则

产品不应把小说创作理解成“一次生成大纲，再连续写完正文”。真实创作通常在构思、人物、结构、场景、初稿和修订之间往返；有的作者先规划，有的作者边写边发现故事，更多作者会混合两种方式。因此系统需要提供清晰的阶段和质量门禁，但不能要求用户在写第一章前穷尽所有细节。

本产品按以下优先级设计：

1. **质量优先**：任何快捷操作都不能绕过人物、关系、世界规则和完整设定审核。
2. **用户掌握创作决定**：AI 可以提出、补全和校验，用户决定哪些内容成为正式写作基线。
3. **渐进式承诺**：先确认足以支撑当前阶段的核心事实；细节允许在后续创作中发现，但变更要有影响分析。
4. **一个规范真相**：正式写作只读取已确认的 `StoryFoundation`，候选、来源证据和正式设定不能混为一谈。
5. **修改可追踪、可恢复**：每轮修改保留 revision、差异、审核结果和回退点。
6. **原创与改编共用主流程**：区别只在来源证据和保留约束；不能为原创维护一套更模糊、更难理解的确认流程。

## 作家视角的完整流程

### 1. 创作意图

用户先给出题材、主题、阅读体验、篇幅、禁区和已有灵感。这里回答的是“我想写什么”，不是要求用户提前写完百科全书。

系统输出：

- 创作简报；
- 尚未决定的问题；
- 对质量影响最大的风险；
- 下一步只保留一个主操作。

### 2. 故事核心与角色候选

AI 根据创作意图提出故事前提、核心角色、重要配角和初步关系。角色卡必须至少包含故事职责、目标、动机、冲突、人物弧和行为/语言约束，不能只有姓名和一句简介。

用户在同一审核工作区完成三种动作：

- **查看全部角色卡**：逐个检查完整内容；
- **让 AI 调整角色卡**：用自然语言说明目标，由 Character Agent 生成新候选并重新独立审核；
- **确认角色卡并继续**：发布 CoreCast，随后生成完整 Foundation。

打开一个停在本阶段的项目时，界面应自动进入“角色卡待确认”，而不是要求用户猜测要去设定中心寻找按钮。

角色卡候选确认与完整 Foundation 确认不是同一数据阶段：前者尚未生成完整世界规则和结构约束，不能假装可以修改不存在的完整设定。但两者必须共用同一套作者交互骨架——查看当前候选、填写明确意见、生成新 revision、重新审核、再次确认。角色阶段的意见直接提交给 Character Agent；“打开角色工作台”只作为逐项检查和高级编辑入口，不能替代当前审核页的意见输入。

### 3. 完整 StoryFoundation

角色确认后，AI 补全目标故事前提、计划关系、世界硬规则和软规则。系统按页签展示概要、角色、关系、世界规则；改编项目额外展示只读原著证据。

本阶段的职责是建立可写作的稳定基线，而不是冻结所有未来细节。硬规则必须明确，软规则允许在后续规划中演化。

### 4. 设定确认与修改

这是进入大纲前的中心审核点，提供两条并列但语义不同的修改路径：

#### AI 智能修改

适用于用户知道想达到的效果，但不想逐项填写字段，例如：

> 加强主角的主动目标，让他和搭档在利益上有冲突，同时保留克制的关系节奏。

系统应：

1. 把意见作为修订目标；
2. 生成新的完整 Foundation 候选；
3. 展示与上一版的差异；
4. 重新执行角色、关系、世界规则和完整 Foundation 审核；
5. 只在用户再次确认后发布。

#### 手工精确修改

适用于用户已经知道字段最终值，例如直接修改人物目标、动机、人物弧、关系标签或某条世界规则。

系统不能把手工输入直接静默写入正式 Foundation。正确处理方式是：

1. 用户编辑现有字段；
2. 前端只提交真实差异，并把新值标记为用户硬约束；
3. AI 仅补齐为消除矛盾所必需的依赖字段，不得重写未列出的设定；
4. 按影响范围重跑审核；
5. 展示差异和审核结果；
6. 用户确认后发布。

这样既保留手工修改的精确性，又避免出现“主角目标改了，但人物弧、关系和大纲仍引用旧目标”的隐性质量问题。

### 5. 宏观结构

Foundation 确认后再生成分卷、主线阶段和关键转折。系统检查：

- 主题与人物弧是否落实到结构；
- 障碍是否迫使人物做出选择；
- 选择是否产生后果并推动下一阶段；
- 主线与重要支线是否在适当位置交汇；
- 长篇节奏是否有重复、空转或过早耗尽。

### 6. 章节规划

在卷级结构确认后生成章节目标、冲突、转折、信息释放和结尾钩子。章节细纲是写作辅助，不应膨胀为替代正文的详尽复述。

### 7. 正文创作

每章写作读取：

- 已确认 Foundation；
- 当前卷/章规划；
- 已发生的连续性事实；
- 人物当前状态；
- 本章必须完成和不能违反的约束。

如果写作过程中发现更好的方向，用户可以提出变更；系统先判断影响范围，再决定只改当前章、重排后续章节，还是发起 Foundation 修订。

### 8. 分层修订

修订顺序应从大到小：

1. 发展性修订：故事承诺、人物动机、人物弧、因果、节奏和世界一致性；
2. 结构修订：场景顺序、重复、缺失转折和信息释放；
3. 连续性修订：时间、地点、人物知识、物件和关系状态；
4. 文风与行文：视角、声音、句段节奏；
5. 校对：错别字、标点和格式。

在大结构仍会变化时过早润色句子，会增加无效劳动，也容易让局部文字质量掩盖整体故事问题。

## 修改影响与质量门禁

| 修改内容 | 最小重算范围 | 必须重跑的审核 |
| --- | --- | --- |
| 措辞、不改变含义 | 当前字段 | schema、语言一致性 |
| 角色描述或语气 | 当前角色及相关场景约束 | 角色完整性、角色声音 |
| 目标、动机、冲突、人物弧 | 当前角色、直接关系、相关大纲 | 角色、关系、因果、完整 Foundation |
| 关系连接或关系动态 | 两端角色及相关结构 | 关系、角色、情节因果 |
| 世界软规则 | 受影响角色与规划 | 世界规则、连续性 |
| 世界硬规则、故事前提 | 全部 Foundation 和全部未发布规划 | 完整 Foundation、结构、连续性 |
| 改编来源角色处置 | 目标角色映射和相关设定 | 原著证据、映射、角色、完整 Foundation |

审核结果分为：

- **阻塞**：矛盾、缺字段、违反硬规则、改编来源映射不完整；不能确认。
- **警告**：可能降低质量但不必阻塞，例如关系网络过于中心化、次要角色作用重复。必须使用中文说明“为什么”和“如何处理”。
- **信息**：设计选择或后续观察点，不制造虚假的错误感。

## 交互状态要求

| 状态 | 中心工作区 | 唯一主操作 |
| --- | --- | --- |
| 角色生成/审核中 | 进度与说明 | 等待生成完成 |
| 角色审核通过、未确认 | 自动展示完整角色候选 | 确认角色卡并继续 |
| 完整 Foundation 生成中 | 生成状态与已确认角色摘要 | 等待生成完成 |
| 完整 Foundation 待确认 | 分页审阅完整设定 | 去确认 |
| AI/手工修改后审核中 | 差异与审核状态 | 等待审核完成 |
| 审核存在阻塞项 | 精确定位问题字段 | 修复阻塞项 |
| Foundation 已确认 | 已发布摘要 | 进入宏观规划 |

“恢复”只负责从安全检查点继续运行；它不应替代角色或 Foundation 的用户确认。若项目停在等待确认状态，点击项目或恢复后应跳转到相应确认区域。

## 原创与改编的边界

两者共用角色审核、完整 Foundation 审核、AI 修改、手工精确修改和最终确认。

改编项目额外具有：

- 永久只读的 `SourceFoundation`；
- 来源角色 keep / merge / exclude 等处置；
- 目标原创角色标记；
- 原著证据和目标设定之间的映射审核。

“其余保持不变”只表示一次局部修订中未列出的**目标设定**不应被 AI 随意重写，不表示改编永远不能改变原著角色。改变原著角色可以是明确的改编决定，但必须在目标设定中显式表达并通过来源映射审核。

## 实现验收标准

- 所有面向用户的生成内容、审核 finding 和错误说明默认使用简体中文；稳定 ID、文件名和必要技术名词除外。
- 角色候选存在时不能显示“0 个角色”或“暂无角色”。
- 打开等待确认的项目，最多一次点击即可到达唯一主操作。
- 角色候选阶段必须同时提供查看、带意见输入的 AI 调整和确认入口；提交意见应直接启动新角色候选，不得先无上下文地跳转到设定中心。
- 完整 Foundation 阶段必须同时提供 AI 智能修改和手工精确修改。
- 手工精确修改只提交差异，不直接绕过审核发布。
- 任何修订都展示 revision、差异、审核结论和可恢复状态。
- 桌面与窄屏下，页签、表单、底部操作和侧栏不得互相遮挡；角色目录与角色正文使用独立滚动区域。
