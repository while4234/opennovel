# DeepSeek V4 Pro / Grok 4.5 上下文基准

## 结论

本次基准支持按模型、按阶段配置，不支持“所有模型统一放大窗口”。更长输入并未稳定提高质量：DeepSeek 的资料分析在 96K 档出现 2/2 可重试失败，Grok 的创作正文在 160K 也没有改善篇幅服从。

推荐的隐藏运行画像：

| 模型 | Coordinator | Architect | Writer | Editor | foundation 合并批次 |
|---|---:|---:|---:|---:|---:|
| DeepSeek V4 Pro | 64K | 96K | 128K | 128K | 40K runes |
| Grok 4.5 | 64K | 96K | 64K | 64K | 60K runes |
| 未识别模型 | 64K | 96K | 96K | 128K | 70K runes |

64K/128K 是在已测 48K、96K、160K 三档之间选取的运行边界，不是额外测试档。其目的分别是给 48K 优胜阶段保留工具调用余量，以及在 96K 与 160K 之间避免过早压缩。

## 试验设计

- 每模型硬上限 40 次调用；DeepSeek 完成 40 次，Grok 完成 38 次，另 2 次在并发策略切换时中断但仍计入额度，未补跑。
- 两模型使用相同阶段任务、相同资料和相同目标档位；生产全局模型包装保持不变，以反映真实运行表现。
- 创作/规划档位为估算 48K、96K、160K；资料分析档位为 12K、24K、48K、72K、96K。
- 每模型最多 3 路并发，模型间可并发；结果先写 started 台账，保证中断不会被重复调用掩盖。
- 评分为 10 分制质量评分，不把速度直接混入质量分。评分依据包括结构/协议合规、任务约束与篇幅服从、信息覆盖、可执行性，并结合代表样本审阅。样本量每个格子仅 1-2 次，因此分数用于工程选型，不视为统计显著性结论。

## 关键负面证据

- DeepSeek 详细提纲 48K：1/2 JSON 截断；96K 与 160K 均 2/2 结构通过。
- DeepSeek 资料分析 96K：一次只返回 16/21 段，一次因长度截断导致 JSON 失效。
- DeepSeek 首次共创：5/6 未严格闭合 `<reply>`，但现有生产解析器会在下一个标签处容错截断，因此属于协议质量问题而非必然重试。
- Grok 资料分析：到 72K 为止 10/10 分段覆盖和 events 上限均合规；96K 有 1/2 超过 events 最多 4 条的约束，但没有遗漏或截断。
- Grok 开篇：48K、96K、160K 均明显短于要求；增加上下文没有解决输出长度问题。

## 文件

- `metrics.json` / `metrics.csv`：逐模型、阶段、档位的聚合指标，不含原文和模型正文。
- `scores.csv`：阶段质量评分、推荐模型和推荐上下文。
- `scripts/analyze_context_benchmark.py`：从工作区外原始结果重新生成聚合指标。

原始响应保留在测试项目的 `.ainovel/benchmarks/context-window-v1`，未提交到 Git，避免把小说资料和大段模型输出带入仓库。
